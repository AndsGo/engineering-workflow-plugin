# Engineering Workflow Plugin v1.1 + v1.2 — Maintenance & Refresh Upgrade

**Status:** Approved (2026-04-30); split into two implementation plans after plan-review round 1
**Date:** 2026-04-30
**Plan split:**
- **v1.1 plan** = `docs/plans/2026-04-30-plugin-v1.1-tier1.md` — Tier 1 only (protocol, frontmatter, hook, retro polish, docs)
- **v1.2 plan** = `docs/plans/2026-04-30-plugin-v1.2-learnings-refresh.md` — Tier 2 (the new `learnings-refresh` skill)
- Reason for split: plan-review-round-1 scope-guardian recommended trim; Tier 2 runs the skill-creator eval loop which has a fundamentally different cadence than Tier 1's prose edits.
**Driver:** Cross-project audit (D:\work\enterprice_agent has 23 active learnings) revealed that the plugin has solid READ/WRITE contracts for `docs/learnings/` but a hand-wavy maintenance layer (knowledge-compound's "Refresh Cycle" is 12 lines, zero automation, zero thresholds). At the project's current trajectory the maintenance gap will become a real problem at ~50 learnings; the upgrade closes it before that point.

---

## 1. Goal

Make `docs/learnings/` a **first-class curated artifact** rather than an append-only log. After v1.1:

1. Every new learning has structured metadata (status, category, last-verified, supersedence) — without breaking the 22+ existing learnings that don't.
2. A dedicated skill (`learnings-refresh`) exists to detect staleness, find duplicate themes, regenerate INDEX, and propose curation actions for user approval.
3. Session-start surfaces a soft signal when learnings exceed configurable thresholds, so the refresh ritual gets prompted without requiring the user to remember the date.
4. `engineering-retro` handles its two most common edge cases cleanly (first-ever retro, solo project) without forcing the user to step around template assumptions.

## 2. Out of Scope (and Why)

| Item | Why excluded |
|---|---|
| Bake project-specific patterns (e.g., "validate at boundary" checklist) into `structured-review` | Violates plugin's existing `docs/learnings/` contract. Project-specific knowledge belongs in the project's learnings, which structured-review already reads. Hardcoding leaks one project's findings into all consumers. |
| New `spec-review` stage between brainstorming and writing-plans | YAGNI. No evidence current `plan-review-personas` is "too late" — needs ≥3 observed cases of "issue should have been caught at spec stage." |
| Backward-incompatible changes to existing learnings | The 22+ existing learnings in real projects are valuable history; any v1.1 design that requires retroactive edits is a non-starter. All new mechanisms must degrade gracefully on frontmatter-less docs. |
| Auto-execute archive/merge actions without user confirmation | Curation decisions need human judgment. Skill produces candidates; user confirms each. |
| Bash port of refresh logic | Decided in brainstorming: Python chosen for maintainability at scale. |

### 3.1 [A1] Frontmatter for `knowledge-compound`

**Affected file:** `skills/knowledge-compound/SKILL.md` (Bug/Knowledge/Decision templates, Cross-reference section)

**Schema** — split into write-side and read-side rules to keep migration painless while still emitting structured data going forward.

**Write side** (what `knowledge-compound` emits for NEW learnings):

| Field | Type | Required on write? | Purpose |
|---|---|---|---|
| `track` | enum: `bug` \| `knowledge` \| `decision` | **yes** | Required by `learnings-protocol.md` WRITE phase |
| `status` | enum: `active` \| `superseded` \| `archived` | **yes** (defaults to `active`) | Required by protocol; nearly always `active` for new docs |
| `category` | string from `references/categories.md` | optional (when categorizable) | Filter by domain in `learnings-refresh` clustering |
| `last-verified` | `YYYY-MM-DD` | optional (defaults to today) | Drives "stale candidate" detection |
| `superseded-by` | relative path | optional (only when `status=superseded`) | Forms supersedence chain |

**Read side** (what parsers tolerate when reading EXISTING learnings, including pre-v1.1):

| Field | Default if absent |
|---|---|
| `track` | `knowledge` |
| `status` | `active` |
| `category` | unset (clustering ignores) |
| `last-verified` | git creation date of file |
| `superseded-by` | unset |

This split means: existing 22+ learnings with no frontmatter continue to work (read-side defaults apply); new learnings always carry at least `track` and `status` (write-side requires); refresh skill can incrementally backfill the optional fields as user reviews each learning.

**Required SKILL.md edits:**

1. Each track template (Bug / Knowledge / Decision) gains a frontmatter block ABOVE the `# Title` line.
2. New section "Frontmatter Field Guide" (after Step 4: Cross-reference) explaining **when each field is non-default**:
   - `category`: fill if the learning maps cleanly to one in categories.md; leave unset otherwise (don't force-fit)
   - `status`: only set non-default when explicitly archiving or superseding
   - `last-verified`: set when the learning was reviewed in a refresh pass
   - `superseded-by`: set together with `status: superseded`; never alone
3. Step 4 cross-reference section gains: "If superseding an existing learning, the new doc sets `status` on its own frontmatter to `active` AND edits the old doc's frontmatter to `status: superseded` + `superseded-by: <new-path>`."

**Acceptance:** A new compound learning emitted by the updated skill includes frontmatter; a learning without frontmatter is still loaded as `track:knowledge, status:active` by `learnings-refresh`.

### 3.2 [A3] Threshold Alerts in Session-Start Hook

**Affected file:** `hooks/session-start`

**Behavior change:** After computing `learnings_count` (line 66-69), compute and inject up to two soft signals:

```bash
LEARNINGS_THRESHOLD_INDEX=${LEARNINGS_THRESHOLD_INDEX:-30}
LEARNINGS_THRESHOLD_REFRESH=${LEARNINGS_THRESHOLD_REFRESH:-50}

learnings_signal=""
if [ "$learnings_count" -ge "$LEARNINGS_THRESHOLD_INDEX" ] && [ ! -f "docs/learnings/INDEX.md" ]; then
  learnings_signal="$learnings_count learnings without INDEX — consider 'refresh learnings'"
fi
if [ "$learnings_count" -ge "$LEARNINGS_THRESHOLD_REFRESH" ]; then
  learnings_signal="${learnings_signal:+$learnings_signal; }$learnings_count exceeds refresh threshold ($LEARNINGS_THRESHOLD_REFRESH) — consider 'refresh learnings'"
fi
```

`learnings_signal` is appended to `state_info` so the model sees it at session start.

**Defaults chosen:** 30 = the point at which a single grep return overflows reasonable reviewer prompt budgets; 50 = the point at which manual curation without tooling becomes painful. Both env-overridable for projects with different cadences.

**Non-goal:** Don't make the hook block, fail, or print noisily when below thresholds. Silence is the default.

**Acceptance:** Hook returns same JSON shape as before; signal appears in state_info only when thresholds exceeded.

### 3.5 [A4+A5] Formal Learnings Protocol

The current plugin treats "read learnings before analyzing, suggest writing learnings after" as an implicit convention — each consumer skill writes its own prose. With v1.1's frontmatter, INDEX, and refresh skill, the convention has too many surfaces to remain implicit. v1.1 elevates it to a **versioned protocol** referenced by every learning-touching skill.

**A4** = the read-phase clause of the protocol, pinned in the always-loaded meta-skill so it gates every session.
**A5** = the protocol document itself + per-skill citations replacing prose.

#### 3.5.1 The Protocol Document

**New file:** `skills/using-engineering-workflow/references/learnings-protocol.md` (~80-100 lines)

Structure:

```markdown
# Learnings Protocol — v1.0

Any skill that reads, writes, or maintains docs/learnings/ MUST follow this protocol.
Skills state their participation phase(s) at the top of their READ/WRITE step.

## READ Phase (analysis skills, before main work)

1. **L1 — INDEX-first:** If `docs/learnings/INDEX.md` exists, read it. Use the Domain
   section relevant to the changed files / scope to build a candidate list.
2. **L2 — Synthesis-preferred:** When the Domain has a 📚 synthesis doc, read it
   FIRST. A synthesis summarizes 3+ individual learnings; reading it can replace
   reading the individuals.
3. **L3 — Targeted reads:** Read individual learning files when the synthesis points
   to them, OR when the Domain has no synthesis.
4. **L4 — Grep fallback:** Use `Grep docs/learnings/` for keyword-precise matches OR
   when INDEX is absent / staleness > 60 days.
5. **Cite sources:** Output the list of learnings consulted (paths) so the user can
   audit. "No prior knowledge applied" is a valid output when nothing matched.

## WRITE Phase (after analysis, when findings are reusable)

1. Suggest `knowledge-compound`; do not write directly. The user opts in.
2. Required frontmatter (per A1): `track`, `category` (when categorizable), `status`,
   `last-verified`.
3. Cross-reference: search for ≥1 related existing learning; add bidirectional
   `Related:` links.
4. Synthesis trigger: if ≥3 active learnings share a category, prompt user to
   consider a synthesis doc instead of a 4th leaf.

## MAINTAIN Phase (periodic, by `learnings-refresh`)

1. Triggered monthly, by user phrase, or when session-start hook signals threshold
   crossed.
2. Never auto-mutate. Detection scripts are read-only; user confirms each action.
3. Preserve INDEX-authored sections by heading allowlist (per §4.3).
4. Apply curation actions (archive / supersede / synthesize) only after explicit y.

## Failure Modes (do not do)

- ❌ Bake project-specific patterns into skill prompts (keep skills general; project
  knowledge lives in project's docs/learnings/)
- ❌ Auto-archive or auto-merge without user confirmation
- ❌ Write learnings without `track` and `status` (other fields optional)
- ❌ Skip INDEX check and grep blindly when INDEX exists
- ❌ Read learnings into the reviewer prompt without citing them in the output

**Versioning note (one line at the top of the doc):** This is protocol v1.0. Breaking changes will document migration when needed.
```

## 4. Tier 2 — New Skill: `learnings-refresh`

### 4.1 Trigger Surface

```yaml
---
name: learnings-refresh
description: "Use monthly, at project milestones, or when LEARNINGS_COUNT exceeds threshold. Audits docs/learnings/ for staleness, missing INDEX, duplicate themes (≥3 same-category), and orphaned references to deleted code paths. Produces a per-learning recommendation table for user-confirmed keep/update/replace/archive/synthesize actions. Triggers on: 'refresh learnings', 'review compound knowledge', 'audit our learnings', 'curate learnings', and after engineering-retro detects recurring patterns."
---
```

### 4.2 Architecture

Progressive disclosure: SKILL.md ≤ 180 lines (workflow + decision tree only); algorithms in scripts; heuristics in references.

```
skills/learnings-refresh/
├── SKILL.md                            # workflow, decision tree, when-to-call-which-script
├── scripts/
│   ├── parse_learnings.py              # → JSON list[{path, frontmatter, headings, code_refs}]
│   ├── detect_stale.py                 # → JSON list[{path, signal: "ref-missing"|"old-and-uncited"}]
│   ├── cluster_by_category.py          # → JSON list[{category, members: [paths]}] for clusters ≥3
│   └── generate_index.py               # → writes INDEX.md from current state (or stdout if --dry-run)
└── references/
    ├── decision-rules.md               # heuristics for keep/update/replace/archive/synthesize
    └── synthesis-template.md           # template for merging ≥3 same-category learnings into one
```

### 4.3 Script Contracts

Each script:
- Stdlib-only (no external pip deps) — frontmatter parsed via simple text split, not PyYAML
- Reads from `docs/learnings/` (path overridable via `--root`)
- Excludes `archive/` and `INDEX.md` and any `.md` without `# ` heading
- Outputs JSON to stdout (machine-readable)
- Exits 0 on success, non-zero on parse errors
- Idempotent and side-effect-free (`generate_index.py --dry-run` is the only mutation, gated by absence of flag)

**`parse_learnings.py`** output schema:

```json
[
  {
    "path": "docs/learnings/2026-04-29-empty-string-lookup-auth-bypass.md",
    "frontmatter": {"track": "knowledge", "status": "active", "last_verified": null, "category": null},
    "title": "Empty-String Lookups in Auth Maps Are Silent Bypasses",
    "track_from_body": "Knowledge",
    "code_refs": ["config/validator.go", "api/key_registry.go", "api/middleware.go"]
  }
]
```

`code_refs` is the list of paths the learning's "Examples in This Codebase" section cites — used by `detect_stale.py`.

**`detect_stale.py`** output:

```json
[
  {"path": "...", "signals": [{"kind": "ref-missing", "ref": "old/path/that/no/longer/exists.go"}]},
  {"path": "...", "signals": [{"kind": "old-and-uncited", "last_verified": "2025-09-01"}]}
]
```

A learning is "old-and-uncited" when last_verified > 180 days ago AND no other learning's `Related:` links to it (orphan).

**`cluster_by_category.py`** output:

```json
[{"category": "pattern", "members": ["a.md", "b.md", "c.md"]}]
```

Returns only clusters ≥3.

**`generate_index.py`**: writes INDEX.md grouped By Domain (via category mapping) and By Track. Idempotent: running twice produces the same file.

INDEX preservation strategy: the script regenerates the **machine-managed sections** (counts, By Domain, By Track, Stats) from scratch. It **preserves verbatim** any section whose heading matches a configured allowlist: `## Refresh Cycle`, `## How to Use This Index`, `## Notes for Future Refreshes`. Sections not in the allowlist are dropped on regeneration. The allowlist is documented in the script and overridable via `--preserve-sections`. The script always shows a diff before writing and refuses to write if it would drop a non-empty unrecognized section (forces the user to either add it to the allowlist or re-author it).

### 4.4 SKILL.md Workflow

1. **Step 1 — Detect:** Run all 3 scripts in parallel, collect outputs.
2. **Step 2 — Synthesize the Recommendation Table:** One row per learning, columns:
   - path | track | status | category | signals | recommended action
3. **Step 3 — Present to User:** Show the table; group rows where `recommended` is the same. Non-active rows go at top (need attention first).
4. **Step 4 — Per-Cluster Synthesis Decision:** For each ≥3 cluster, ask "synthesize? (y/n/skip)". On y, draft a synthesis doc using `references/synthesis-template.md` and ask user to review before writing.
5. **Step 5 — Per-Row Action:** For each non-keep row, confirm the action with the user. Apply only after explicit y.
6. **Step 6 — Apply:**
   - Archive: `git mv path archive/<basename>`; do not edit content.
   - Update: open the file, ask user what to update, edit, set `last-verified` to today.
   - Replace: write new doc, set old doc's `status: superseded` + `superseded-by`.
   - Synthesize: write synthesis doc, set members' `Related:` lines to point to it (don't archive members — synthesis adds, not subtracts).
7. **Step 7 — Regenerate INDEX:** Run `generate_index.py` (no --dry-run). Diff and present.
8. **Step 8 — Commit suggestion:** Print suggested commit message; do NOT auto-commit.

### 4.5 Decision Rules (`references/decision-rules.md`)

| Signal | Default recommendation | Reason |
|---|---|---|
| `ref-missing` (cited path no longer exists) | candidate `archive` | Code that grounded the learning is gone; learning may be wrong now |
| `old-and-uncited` (180+ days, 0 inbound Related:) | candidate `archive` | Probably never reused; check before archiving |
| Cluster ≥3 same category | candidate `synthesize` | Worth rolling into one doc with cross-references |
| Decision-track learning, any stale signal | candidate `supersede` (NOT archive) | Decisions retain rationale; supersede via new doc preserves history |
| Bug-track learning, last-verified > 90 days, ref-missing signal | candidate `archive` (user confirms bug class is extinct) | Script cannot prove "fix verified in test"; user must confirm |
| status=`superseded` for ≥1 refresh cycle | candidate `archive` | One cycle's grace period to surface broken inbound links |

The 90-day and 180-day thresholds are configurable via `--stale-days` and `--orphan-days` script flags; defaults reflect the cadence at which a typical project's learnings mature.

## 7. Risks and Open Questions

| Risk | Mitigation |
|---|---|
| Python stdlib frontmatter parsing edge cases (multi-doc YAML, escaped chars) | Restrict to simple `key: value` lines; document the constraint in SKILL.md; reject and warn on complex YAML |
| `generate_index.py` overwriting user-authored INDEX content | Heading-name allowlist (preserve `## Refresh Cycle`, `## How to Use This Index`, `## Notes for Future Refreshes`); diff-before-write; refuse-on-unknown-non-empty-section |
| `detect_stale.py` false positives when code was renamed but path matches another extant file | Document limitation: "ref-missing" is best-effort; user must confirm |
| Cluster threshold of 3 producing too many synthesis prompts on small projects | 3 is the minimum useful count; smaller is noise. Eval case 5 verifies the threshold is right. |
| `learnings-refresh` invoked monthly but project has no new learnings | Step 1 detects `last refresh > 30d ago AND 0 new files since`, skips and reports "no work needed" |
| Protocol becomes a doc nobody reads | Always-loaded meta-skill cites it explicitly; consumer-skill citations make compliance visible in code review; protocol violations show up as missing citations in skill output |
| Protocol drift from skill behavior | Protocol is the single source; skills cite, never inline. Updates to protocol cascade. CI lint (future) can grep for citations to verify presence |
| Per-skill semantic filtering (security-audit's category list) buried under "follow protocol" reference | Spec keeps per-skill domain filtering guidance in the skill itself; protocol covers shared mechanics only |

## 9. Sequencing

1. Spec approval (this doc)
2. Implementation plan (`writing-plans` skill produces `docs/plans/2026-04-30-plugin-v1.1-upgrade.md`)
3. Plan review (optional `plan-review-personas`)
4. Tier 1 execution (4 atomic tasks; ~half day)
5. Tier 2 design refinement (clarifying questions if any) → draft → eval loop → iterate → done

Tier 1 must precede Tier 2: `learnings-refresh` reads frontmatter that A1 produces, surfaces signals computed against A3's thresholds, and **implements the MAINTAIN phase that A4+A5's protocol defines**. Specifically, A4+A5 should land before A1's frontmatter rollout in the implementation order, because the protocol document is what governs A1's frontmatter shape.

**Full v1.1 sequence:**

```
A4+A5 (protocol + citations)
    ↓
A1 (frontmatter — protocol-conformant)
    ↓
A3 (hook thresholds)
    ↓
C1, C2 (engineering-retro polish — independent, parallel-safe)
    ↓
Tier 2 (learnings-refresh — full skill-creator eval loop)
    ↓
A6 (documentation sync — runs LAST; reflects actual final state, not planned state)
```

A6 deliberately sits at the end so it captures the as-shipped behavior of every preceding change. Running A6 earlier risks documenting plans that get revised during implementation.
